Order lifecycle

NEWCreated at the till, payment taken
PREPARINGFood counter taps Start
READYFood counter taps Ready, name called out
COLLECTEDHanded over, card leaves the screen
CANCELLEDTill only, before Start. Excluded from sales

Each step stamps its own time (createdAt, startedAt, readyAt, collectedAt), so wait time and the peak window come straight from the data.

Data model

orders/{autoId} orderNo "A-043" device letter + daily seq name "Priya" called out at the pass items [{id, name, qty, price}] total 1500 pence, no float maths payment "cash" | "card" status new | preparing | ready | collected | cancelled day "2026-10-17" index: day + createdAt createdAt · startedAt · readyAt · collectedAt till "A" menu/{id} name · short · price · colour · active · sort

Order numbers are generated on the device (A-001, A-002…; a second till uses B-), so the till never waits on the network. Prices live in the menu collection, edited in the Firebase console in Phase I.

Free-tier fit

500 orders in a day is about 2,500 writes (limit 20,000) and about 12,000 reads across four screens (limit 50,000). No billing account on the Spark plan, so nothing can be charged; over quota, Firestore pauses until the quota resets.

No login, with guardrails

Firebase anonymous auth runs silently on load (no screen). Security rules accept only signed-in devices and order-shaped documents, and block deletes. The URL is shared only with volunteers. PINs per counter come in Phase II.
